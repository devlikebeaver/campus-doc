# 문서별 추출과 중앙 양식 관리

기존 문서에서 새 디자인 시스템을 얻고, 같은 기관·문서 종류의 다음 작업에서 그 양식을
다시 사용하는 흐름이다. 사용자는 자연어로 등록·조회·선택을 요청한다.

## 스킬의 첫 진입점

문서 작업을 시작할 때 `scripts/registry.py list`로 중앙 레지스트리를 갱신하고 읽는다.
위치는 `library/registry.json`이다. 양식 위치·문서 종류·기관·부서·사용 여부·우선순위,
검토 상태, 최신 컴포넌트와 양식 버전, 사용자가 지정한 기본 선택을 이 파일에 모은다.
경로는 레지스트리 폴더를 기준으로 저장한다.
같은 드라이브는 상대 경로를 사용하고, Windows의 다른 드라이브에 연결한 외부 폴더는
절대 경로로 저장한다. 다른 PC로 옮겼을 때 외부 폴더 연결은 다시 확인한다.

기본 검색 위치는 `assets/`다. `manifest.json`과 `package-base.zip`을 가진 양식 전용
폴더를 발견하면 등록한다. 임의 파일 하나가 있다는 이유로 양식으로 선택하지 않는다.
외부 위치는 `registry.py watch DIRECTORY`로 검색 위치에 등록할 수 있다.

선택 순서는 다음과 같다.

1. 사용자가 양식을 지정하면 그 양식을 사용한다.
2. 문서 종류와 기관·부서가 맞는 후보를 찾는다. 정보가 명시되어 다른 기관·부서인
   양식은 제외한다.
3. 조건이 맞는 후보 가운데 사용자가 지정한 기본 선택을 우선한다. 같은 조건이면
   추가 양식의 기본 우선순위가 기본 예시보다 높다.
4. 최고 우선순위 후보가 여럿이면 이름과 검토 상태를 보여주고 선택받는다.
5. 비활성·누락·구조 검토 실패 양식은 사용하지 않는다. 외형 검토가 남은 양식은
   그 상태를 유지한 채 시험 문서로 생성한다.

양식 선택과 컴포넌트 버전 선택은 구분한다. 최신 버전은 목록에 표시하지만 저장된
양식이 고정한 이전 버전을 조용히 최신 버전으로 바꾸지 않는다.

```text
python -X utf8 scripts/registry.py list
python -X utf8 scripts/registry.py select --kind plan --institution 예시대학교
python -X utf8 scripts/registry.py prefer my-campus-plan
python -X utf8 scripts/registry.py prefer auto
python -X utf8 scripts/registry.py watch ADDITIONAL-FORM-DIRECTORY
```

메타데이터 수정은 `configure COLLECTION PATCH.json`을 사용한다. 자연어에서
기관·부서·문서 종류와 사용 여부를 받아 에이전트가 내부 입력을 작성한다.
경로·검토 완료 상태는 일반 메타데이터 수정으로 임의 확정하지 않는다.

## 새 전용 폴더로 추출

기존 `assets/plan`, `assets/report`를 유지하고 새 폴더를 같은 위치에 만든다.
이미 있는 폴더를 덮어쓰지 않는다.

```text
assets/
  plan/                      기본 운영계획서 컴포넌트
  report/                    기본 결과보고서 컴포넌트
  my-campus-plan/              문서별 추가 양식
    source/                  원본 사본, 준비된 HWPX, 참조 PDF
    components/              독립 XML 컴포넌트
    binary/                  원본 네이티브 HWP 컴포넌트
    examples/                원형 데이터
    reviews/                 검토 트리와 반복 검토 기록
    manifest.json            조합 순서와 원본 대응
    tokens.json              실제 글꼴·자간·색·테두리 정의
    field-schema.json        내용 슬롯의 스타일
    package-base.zip         해당 문서의 스타일·이미지 자원
library/
  registry.json              스킬이 읽는 중앙 목록
  components/               사용자 컴포넌트 버전
  templates/                사용자 양식 버전
```

`import_document.py extract SOURCE --name COLLECTION`은 HWP/HWPX를 추출한다.
기관·부서는 `--institution`, `--department`, 문서 종류는 `--kind`로 기록한다.
HWP는 HWPX 분석본과 네이티브 바이너리를 함께 보관한다. 원본은 바꾸지 않는다.
PDF는 `--reference-pdf`로 지정하는 외형 기준이다.

배포 예시와 문단 구조가 같은 문서를 그룹으로 추출하려면 `--profile plan` 또는 `--profile report`를
사용한다. 다른 문서는 최상위 문단별 후보부터 추출한다. 후보가 모두 의미 있는 완성
컴포넌트라는 뜻은 아니다. 분석 후 `--groups GROUPS.json`으로 표지·본문 제목·목록·표를
묶어 새 추출본을 만들 수 있다. 그룹은 모든 문단을 원본 순서로, 중복 없이 포함해야 한다.
페이지 힌트가 없으면 실제 페이지 번호를 추측해 채우지 않는다.

새 컬렉션은 독립 스타일 기준을 사용한다. 서로 다른 문서의 같은 숫자 스타일 ID를 같은
서식으로 취급하지 않는다. 다른 컬렉션 컴포넌트를 한 양식에 넣으려면 스타일·이미지
자원의 명시적인 가져오기와 참조 재연결을 먼저 구현한다.

## 재귀 검토와 반복

`review PROJECT`는 컴포넌트에서 자식 도형·표·셀·문단·run·문자열까지 내려간 트리를
만든다. 글꼴·자간·장평·크기·불렛·선·색·셀 여백은 `tokens.json`과 트리의 스타일 참조·
속성을 함께 추적한다. 셀을 떼어 놓고 상위 표의 병합·배치를 잊지 않는다.

1. 구조 검사: 스타일·이미지 참조, 표 병합, 원본 섹션과의 재조합, 추출 자원 해시.
2. 의미 검토: 컴포넌트 경계, 표지와 본문 구분, 반복 요소와 입력 내용의 구분.
3. 외형 검토: 같은 렌더링 환경에서 원본과 재구성본의 각 페이지를 확인한다.
   첫 페이지 자간, 실제 해석된 글꼴, Wingdings 불렛, 헤더·CI, 표 높이·선·셀 여백을
   따로 비교한다.
4. 문제 있는 상위 컴포넌트에서 관련 자식 요소까지 내려가 원인을 찾고 새 버전으로
   수정한다. 검토 입력 해시와 수정 대상을 기록하고 다시 생성·검토한다.

검사할 때마다 `reviews/iteration-NNNN.json`이 생기고 이전 기록은 보관한다. 구조 검사
통과만으로 의미·외형 상태를 완료로 바꾸지 않는다. 현재 자동 검토는 구조와 재귀 트리
제공까지이며, 의미·외형 판단과 수리는 에이전트가 실제 자료를 보고 수행한다. 자동으로
모든 결함을 찾아 수정하는 완성 루프라고 설명하지 않는다.

`rebuild PROJECT OUTPUT.hwpx`는 컴포넌트를 원형 순서로 재구성한다. 다중 섹션도
보존한다. HWP에서 추출한 경우 `.hwp` 재구성은 네이티브 바디 레코드가 원본과 같은지
검사한다. 이 경로는 원형 추출 검증용이다. 내용·디자인 변경은 버전 관리 생성·수정
기능을 사용하고 별도로 렌더링한다. 다중 섹션의 새 순서 조합은 아직 지원하지 않는다.

“이 문서를 새 양식으로 등록해서 다음부터 써줘”라고 하면 추출·메타데이터 등록,
검토, 기본 선택을 수행한다. 공용 기본 컴포넌트를 자동으로 덮어쓰지 않는다.

## 검사

`check_registry.py`는 전용 폴더 추출, 모든 자식의 재귀 트리, 검토 이력, 원형 재조합,
추가 양식 발견, 기관 조건 선택, 후보 충돌, 기본 선택, 비활성·구조 실패 제외,
임의 문단·다중 섹션 추출, 외부 폴더 등록, 원본 불변을 실제 파일로 시험한다.
네이티브 화면 비교와 Gemini 앱의 올인원 설정은 별도 확인이 남아 있다.
